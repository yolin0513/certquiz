## 設計前提：本機自用 vs 公開散布（接手前一定要先懂）

這個 repo 與網站都是**公開**的（GitHub Pages）。TABF 官方試題的處理方式由這條界線決定：

| | 本機自用 ✅ 做 | 公開散布 ❌ 不做 |
|---|---|---|
| 內容 | 在 使用者的電腦上把官方 PDF 轉成題庫檔，他匯入**自己的手機** | 題庫檔進 repo、上網站、內建在 App |
| 放哪 | `refs/`（PDF）、`data/local/`（題庫檔），`.gitignore`＋commit 前自查雙重擋 | — |
| 誰拿得到 | 只有他 | 任何人 |

- 轉檔**腳本**進 repo（不含題目內容），換電腦可重跑；**題庫檔**永遠不進 repo。
- 公開網站上只有練習引擎和原創題。
- 著作權法第 9 條第 1 項第 5 款「依法令舉行之考試試題」是否適用於這張測驗：智慧局函釋（電子郵件1041201）以本測驗的法源為例、條件式肯定，但自稱非主管機關、建議洽金管會；**不是確定結論**（見 `H_TABF題庫與法律問題.md`）。**因為題目不散布，這個法律問題對本專案不構成風險；把題目改成公開，要 使用者本人看過依據強度後拍板。**

## 範例：怎麼做一次不騙自己的量測（2026-10-08，讀書模式第 2 步，Dispatch 指定為專案範例）

內控主題分組的驗收（`docs/K_讀書模式方案.md` 第 2 步；程式 `scripts/study_points.py`、`study_split.py`、`study_topics.py`、`study_eval.py`）。結果是**沒過**，但這一輪的做法是之後所有量測的範本：

1. **門檻、分母、樣本數事先寫死**（寫進文件、寫進程式、提交後才抽樣），結果出來後一個都沒動。「說不準」算進分母、3 倍用乘法——在看到資料前就定了對自己不利的算法。
2. **以考點為單位切開發／驗收組**，同一考點的題整組放同一邊，避免「開發組讀過的題，它的雙胞胎落在驗收組」讓驗收數字偏高。
3. **先存檔、記雜湊、核對沒被改過，才揭曉**：判斷檔鎖定時把 sha256 記進只往後加的 `log.tsv`；揭曉程式先核對雜湊，不同就拒絕。抽樣、凍結規則也都記雜湊、拒絕重做。
4. **規則沒定義的情況，程式停下來**：切分時發現 6 個考點橫跨兩科，程式照設計中止、不寫檔；補規則之後才往下，而且當時還沒產生任何結果——所以補規則不是為了遷就結果（文件記下了這一筆）。
5. **量測沒過，備案照事先寫的執行，沒有回頭修判準**。
6. **報數字時成對報**：同組 11% 是跨組 1% 的 11 倍，但絕對比例只有 11%、偏誤方向是高估——兩個數字一起看才有意義，分開引用任何一個都會誤導。
7. **已知偏誤照實寫**：判斷者就是分組者（知道規則），方向是高估；有偏誤但方向已知的量測仍然比沒有好，但讀數字要往下打折。

13. **「擋下」要核對理由，不能只看回傳值**（2026-10-08 起）。
    - **起因**：pushsafe 驗法在 Windows 上叫到 System32 的 WSL bash（沒裝發行版），五個情境全都沒跑起來；其中四個「應該擋下」的情境因為**失敗的回傳值剛好等於擋下的回傳值**，被算成通過。也就是**閘門完全沒運作的時候，它的自我測試顯示全綠**——這是最糟的失效：不是沒擋，是沒擋還告訴你擋住了。
    - **理由**：只看「有沒有失敗」分不出「規則擋下」和「程式根本沒跑」；要看「擋下的理由是不是我造的那一個」。
    - **做法**：凡是「預期會擋下／會失敗」的測試情境，判定必須同時核對①回傳值、②行首判定行裡的**指定理由**（點名的規則、題號、檔名）、③副作用的狀態（例如假遠端沒變、沒寫出檔）。沒有判定行就判「情境未成立」，不算通過。量測工具（網路監測、掃描器）要先用已知樣本證明抓得到，再拿它下「沒有發生」的結論——**抓不到和沒有發生，在輸出上長得一樣**。
    - Windows 上從 Python／node 叫 bash 一律用 `shutil.which("bash")` 的完整路徑（Git Bash）。
    - 尚未補理由核對的檢查清單見「已知不一致與技術債」。
14. 量測先驗尺：任何「沒有 X」的結論（沒有外部請求、沒有洩漏、沒有命中），量測工具都要在同一次執行裡先用一個刻意造出的 X 證明抓得到；驗尺失敗就整個中止，不下結論。
    - **造錯的方式**（2026-10-08，見「踩過的坑」的瀏覽器換行那一條）：要證明檢查量得到，**必須造一個必定會產生那個現象的錯，不能只拿掉一個「理論上」在防它的設定**——那個設定在當下的情境可能根本沒作用，拿掉它等於沒改，檢查不紅也證明不了任何事。反對照沒變紅時，先問「我改的東西在這裡真的有作用嗎？」。
15. **掃描的母體要從 git 自己數出來，不能沿用先前回報裡的數字**（2026-10-08）。部署前曾照回報說「13 個 commit」，實際用 `git rev-list --all` 數是 16 個——照 13 個去掃會漏掉 3 個，而且不會有任何徵兆。檢查程式與回報一律寫「實際數到幾個、掃了幾個」，兩者要相等；commit、檔案、題目、路徑都一樣。
    - **範例（比規則本文更有說服力）**：`test_verify_live.py` 的突變「靜默跳過中文檔名」——它**沒有當掉、不一致清單是空的，看起來完全像全部通過**，唯一露出馬腳的是「比對 1／3」那個數量。所以每個檢查都要印母體數字（比了幾個／應該比幾個），不能只印「發現幾個問題」；只印問題數的檢查，在這種失效下會顯示「0 個問題」。
16. **任何回報「命中 0」的檢查，同一次執行裡必須附一個已知會命中的正對照**（2026-10-08）。沒有正對照的 0，只能寫成「在已比對範圍內未見」，不能寫成「沒有」。本專案已照做的地方：瀏覽器監測器（驗尺 R1～R5）、歷史掃描（假樣本 6 個逐一點名）、線上比對（驗尺 V3：已知檔回 200；V4：真題幹餵進比對必中）、`test_verify_live.py`（正對照 B：中文檔內容不同必須點名）。
    - 正對照只證明「抓得到那一種」；覆蓋範圍要另外寫明。例：R7 題幹比對是 **793／796** 個不重複題幹——3 個不到 12 字的通用句（如「下列何者非屬有價證券？」）為了避免誤判沒有拿來比，**那 3 題如果洩漏到公開檔案裡，這道檢查抓不到**。

- **TABF 試卷是 A3 雙欄**：`pdftotext` 直接抽，題號左右交錯（14 15 1 16 2…）；要逐頁切欄。

- **`pdftotext -table` 讀答案卷會整欄錯位一列**（表頭那列吃到第 1 題的答案）——答案錯位在真實工具裡就會發生，所以答案一定要兩條獨立讀法逐題比對（`-raw` 逐列、`-simple` 依水平位置）。
- **heredoc 裡用 Python 做字串取代，`\n` 很容易被寫成真的換行**（2026-10-08 踩了三次，把程式檔寫壞，其中兩次是先寫檔才編譯；連這一條紀錄本身和上一條的 `\f` 都被寫壞過）。**改程式碼一律用 Edit 工具。**非用腳本不可時，用 `chr(10)`、`chr(92)` 組字，並且先編譯檢查、通過才寫檔。
- **重跑抽樣腳本會蓋掉已填的核對紀錄**（2026-10-08：為了確認可重現而重跑 `sample_check.py`，把 40 題的核對紀錄蓋掉，事後依原紀錄補回並在檔內註明）。已改成檔案存在就不覆寫，要重寫須加 `--force`；兩向都在暫存複本驗過。
- **Windows 上 Python 用 subprocess 叫 `bash` 會找到 System32 的 WSL bash**（沒裝發行版就跑不起來；`shutil.which` 卻回 Git Bash，兩者搜尋順序不同）。2026-10-08 pushsafe 驗法五個情境全都沒跑起來，其中四個「擋下」的情境因為也回 1 而顯示通過——**只看回傳值的測試會把當掉算成擋下**。已改成用完整路徑，並要求每個擋下都附指定理由。
- **被瀏覽器預設行為救了的等價突變**（2026-10-08，M3 依據網址的版面檢查）：為了證明「手機寬度不橫向捲動」量得到，第一個反對照是拿掉長網址的換行 CSS（`overflow-wrap: anywhere`）——**結果沒變紅**。原因：Chrome 本來就會在網址的 `/`、`-` 處換行，那條 CSS 在這些網址上根本沒作用，所以拿掉它等於沒改。
  - **陰險的地方**：你以為自己在測版面，實際上是瀏覽器的預設行為在撐；不管版面寫得對不對都不會紅。檢查本身是對的、突變也「看起來」合理，兩者都沒錯，錯在突變沒有真的改變被量的東西。
  - **修法**：改用 `white-space: nowrap` 強迫不換行，文件寬變成 1017px（視窗 375px），檢查才變紅——證明量得到。
  - **通則**：反對照沒變紅時，先問「我改的東西，在這個情境下真的有作用嗎？」，不要直接下結論說「檢查壞了」或「程式碼本來就對」。要確定量得到，就造一個**必定**會產生被量現象的錯（直接強迫溢出），而不是拿掉一個「理論上」防止它的設定。

- **一張證照的題庫讀不到，整個首頁就掛掉**（2026-10-08，加 AZ-900 時發現）：首頁逐張證照讀題庫，任何一張失敗就整頁出不來，連使用者匯入的內控題也進不去。改成每張卡片各自處理錯誤，並加測試（題庫檔不存在時首頁照常、AZ 卡片顯示「題庫暫時讀不到」）；拿掉這個處理時測試會紅。
- **答題後出現 `nullnull`**（2026-10-08 使用者在 iPhone 回報）：原因不是欄位本身，是寫法——回饋區用瀏覽器原生的 `replaceChildren(…, 解析 ? 段落 : null, 依據 ? 段落 : null)`，原生的 `replaceChildren` 會把 `null` 轉成文字 "null"；自寫的 `h()` 會略過 null，所以同樣的條件寫法在 `h()` 裡沒事、在 `replaceChildren` 裡就出事。TABF 題沒有解析與依據，兩個 null 就印成 `nullnull`。
  - **同一個寫法的其他地方**：模擬考全部答對時成績頁也會印 "null"（`render` 底層同樣是原生 `replaceChildren`）；另外查出同類的「缺欄位印出 undefined」：出處標示有期別沒題號會印「第 undefined 題」、匯入失敗的錯誤訊息會印「版本 undefined」「證照：undefined」、統計頁沒有科目的題目分組名稱是空白。
  - **修法**：放進畫面一律經過 `fill()`／`render()`（先濾掉 null／undefined／false）；出處與錯誤訊息逐段只在欄位存在時才出現；統計的空分組名稱顯示「未標示」。
  - **防線**：①`test_logic` 靜態檢查 `app.js` 直接呼叫 `replaceChildren` 的只准 `fill`、`render` 兩處；②瀏覽器測試的全畫面掃描——每個測試頁面都有監看器，任何時刻畫面文字出現 null／undefined／NaN 就記下來，整個測試結束時必須是 0（驗尺：先放一段 nullnull 必須被抓到）；③「最小題目」（匯入檢查接受的最少欄位）走完整流程＋格式錯誤的匯入包＋模擬考全對。修之前跑過：紅 4 項；三個突變（clean 不過濾、錯誤訊息直接印缺的欄位、新增一處直接呼叫 replaceChildren）都會紅。

  - **我做了什麼**：在查清楚之前，我刪了 6 個當時沒有程序在用的 `puppeteer_dev_*` 目錄（以為是本專案的殘留，很可能其中有其他專案的）；還有一次清理程式碼對一個 MealMate 正在使用的目錄執行了刪除（被鎖住沒有整個刪掉，但可能刪到其中沒被鎖的檔案；之後那個目錄已不存在，無法判斷是 MealMate 自己清的還是受我影響）。

- **只靠顏色傳達資訊**（2026-10-08，讀書模式設計時）：正解除了綠底，另加「（正解）」字樣。只靠顏色的話，色覺差異或深色模式下可能完全讀不出來——使用者的手機就是深色模式。之後所有「對／錯／重點」的標示都要有文字或符號，不能只有顏色。

  - **原因**：App 的連結都靠各元件自己的類別（`.btn`、`.back`）上色，大綱頁的 57 個細項連結沒有類別，就落回瀏覽器預設——未點過 #0000ee、已點過 #551a8b。在深色卡片（#1c2229）上對比只有 **1.71:1 與 1.46:1**（WCAG AA 一般文字要 4.5:1）。主題色本身都過（最低 4.78:1），問題只在「有元素沒套到主題色」。首頁按鈕是 `flex-wrap`，寬度跟著字數走，兩張卡片的按鈕數又不同，所以排法完全不一樣。
  - **為什麼之前沒發現**：之前的瀏覽器測試只在無頭瀏覽器的預設（淺色）模式下跑，沒有任何一道檢查在算對比，也沒有檢查「每個連結都套到主題色」；淺色底上預設藍（#0000ee 對白 9.4:1）其實讀得到，所以淺色下看不出問題。**我看起來可以，是在我的螢幕上**——要靠計算，不靠眼睛。
  - **修法**：①全域 `:where(a) { color: var(--pri) }`——權重 0，各元件自己的顏色一定蓋得過；**不寫 `a:visited`**：它的權重（0,1,1）比 `.btn`（0,1,0）高，會讓點過的按鈕文字變藍。②大綱細項改成可點的列（`.item`：邊框、題數、「›」），讀過的用文字「✓ 已讀」標，不靠連結顏色。③首頁按鈕改兩欄等寬格線、每排等高；兩張卡片的順序固定為讀書、開始練習、錯題複習、統計，再接模擬考；錯題數改成「錯題複習 12」，三位數在 320px 也是一行。④「模擬考：（實務）」的括號不是漏字：官方試卷上第二科的科目名是「銀行內部控制與內部稽核（一般金融類）」，本來就沒有「實務」兩字；「實務」是本專案自己的稱呼，按鈕用剝掉前綴的科目名，就剩「（實務）」。改成科目加 `short`（法規／實務），按鈕與讀書頁都用它。
  - **防線**：瀏覽器測試「二之八」，深色、淺色各跑一輪（**有母體**：另外從整個 body 走每個看得到的文字節點算「畫面上的文字元素」，必須剛好等於量到的「算對比＋停用豁免」，不相等就紅並點名漏掉的元素；目前 12 個畫面 2,100＝2,100。突變：把選擇器縮成只看卡片內，母體 2,103、量到 2,081，紅並點名標題與「← 回首頁」），iPhone 390×844：12 個畫面逐一找「直接含文字」的可見元素，算文字色對實際背景（往上疊到不透明為止）的 WCAG 對比，一般文字低於 4.5:1、大字低於 3:1 就紅；停用的按鈕依 WCAG 1.4.3 豁免但另外計數。連結、按鈕、輸入框的文字色必須是主題色之一。`getComputedStyle` 看不到 `:visited` 的樣式，所以另外掃樣式表，有 `:visited` 規則就紅。首頁在 390 與 320 兩種寬度量按鈕：兩欄、等寬、等高、兩張卡片欄位置對齊。驗尺：同一套公式對 WCAG 已知值（#767676／白 4.54 過、#777777／白 4.48 不過）。突變：說明文字調暗、重現原本的預設連結、按鈕改回 flex、加一條 `:visited` 規則，四個都會紅、紅在對的那一項。
  - **途中抓到測試自己的一個「靠運氣才綠」**（機制已用實驗確認，寫清楚是為了讓下一個人認得同類問題）：
    - **斷言**：首頁內控的按鈕要顯示「錯題複習 1xx」（三位數），用來證明三位數在 320px 也排得下一行。
    - **準備資料的寫法**：從錯題表**取第一筆**來複製 120 份，假設第一筆一定是內控的。
    - **那個假設什麼時候不成立**：同一個測試前面的畫面巡覽，深色、淺色各答一題 AZ-900（隨機抽題、固定點選項 1）。答錯就會寫一筆 az900 的錯題，錯題表依題號排序，`az900-…` 排在 `bic-…` 前面，120 份就複製到 AZ 去了，內控還是個位數，斷言變紅。
    - **所以綠或紅取決於兩件測試沒控制的事**：①AZ 那兩題答錯沒有（隨機抽題，選項 1 剛好是正解的機率約 1/4）；②那筆作答有沒有真的寫進去——App 先顯示對錯、**再**寫 IndexedDB，測試看到對錯就做下一步並重新載入頁面，重新載入會中斷還沒寫完的交易。實驗：在舊寫法上記下灌資料當下的 AZ 作答紀錄，3 次裡有 1 次只剩 1 筆（另一筆被中斷吃掉）。
    - **量到的通過率**：同一份舊寫法，加 `gotoView` 之前 6 次綠 5 次；之後我用舊寫法重跑 5 次只綠 1 次。兩者差在哪裡**沒有查清楚**（可能是機器負載影響寫入有沒有被中斷，未證實）。重點是：這條斷言的結果由隨機抽題與時序決定，不由版面決定——綠的時候它沒有在守任何東西，而測試報告上看不出差別。
    - **修法**：①指定挑內控的錯題，不靠位置；②**固定先放一筆排第一的 AZ 錯題**，每次都重現「第一筆不是內控」的情況；③灌完讀回內控錯題筆數，≥120 才往下（準備步驟本身也是一條斷言）。改回舊寫法，這兩項都會紅。
    - **怎麼認同類問題**：測試準備資料時「取第一筆／取任一筆」，而資料表裡的內容又受同一個測試前面的隨機步驟影響——結果就由執行順序與時序決定。準備步驟要指定條件，並且讀回確認。
    - **順帶發現的 App 行為**：練習時是先顯示對錯、再寫作答紀錄；顯示後幾毫秒內重新載入或關頁，這一題的作答會遺失。對人手操作幾乎不可能發生，暫不改，記在這裡。
  - **通則**：只要畫面上有一個元素沒套到主題，深色模式就會露出瀏覽器預設值；「看過幾頁沒問題」不算檢查，要掃全部畫面、列出母體。
- **Write 與 Edit 工具都會把內容裡的 `\u00a0`、`\u200b` 這類跳脫字寫成真的不可見字元**（2026-10-08，`verify_basis.py`、`build_data.py` 中過；**連記錄這一條的 STATUS 本身也中了**——寫這一條時用 Edit 工具，兩個跳脫字被換成真字元，是新加的掃描第一次跑就抓到的）。
  - **危險在於它在螢幕上和空白一模一樣**：程式壞掉時，你會看著「正確」的程式碼找不出問題；diff 也看不出差別。
  - **防線**：commit 前自查 R8——要入庫的文字檔不得含不可見字元（NBSP、窄 NBSP、零寬空白／連接／不連接、word joiner、BOM、軟連字號），逐一點名行、欄與字元名稱；`--selftest` 有含這些字元的假樣本證明會紅。秒級。
  - **寫法**：程式碼與文件裡要提到這些字元，一律寫跳脫形式；用腳本寫入時以 `chr(92)` 組出反斜線，不要在工具內容裡直接打 `\u…`。
  - **已知、刻意不處理**：git 歷史裡有 5 個舊版本含這類字元——`scripts/verify_basis.py` 在 `6e2875b`、`d42127f`、`5c65685`，`docs/STATUS.md` 在 `0cae467`、`8524ab2`。改寫已推送的歷史代價遠大於影響（Dispatch 2026-10-08 同意不改）；R8 只擋新進來的，所以 `--history` 不查 R8。
- **GitHub Pages 專案站的 robots.txt 無效**：專案站在子路徑（`…github.io/<repo>/`），搜尋引擎只讀網域根目錄的 robots.txt。本專案不放 robots.txt，靠 `index.html` 的 noindex meta；GitHub Pages 也不能設 X-Robots-Tag 標頭。
- **Cloudflare Pages 已併進 Workers**（RentCheck 的經驗）：`wrangler pages project create` 會失敗，要用 `wrangler.jsonc` 的 Workers 靜態資產＋`wrangler deploy`。

## 已知平台行為

會讓「看到的」和「實際的」不一樣的工具／平台行為。每一條都是踩過才寫的。

- **Python 的輸出寫到檔案或管線時會先暫存，程式結束（或暫存滿）才一次寫出**（2026-10-08，外觀突變的背景執行：跑了二十多分鐘，輸出檔一直是空的，結束時才一次出現全部結果）。輸出到終端機時是逐行寫出，所以在前景跑的時候看不出來。
  - **危險**：中途讀到的是**空白**——「還沒寫出來」和「什麼都沒發生／卡住」完全分不出來。這和「讀到寫到一半的輸出」（JLPT 2026-10-08 的事故：停在全綠的地方，差點據此回報通過）是同一件事的兩種形狀：中途的輸出不代表結果。
  - **規則**：背景跑 Python 一律 `python -u`（或 `PYTHONUNBUFFERED=1`）；判斷結果只看最後的結論行（`… OK`／`… FAILED`、結束碼），不看「輸出看起來寫完了／是空的」；長跑丟背景後留在前景輪詢，不待機等通知。
- **IndexedDB 的寫入在頁面重新載入時會被中斷**：還沒完成的交易直接消失，不報錯。測試看到畫面變化就換頁，可能比 App 的寫入早（見「踩過的坑 → 外觀」那一條的實驗）。
- **只改網址 `#` 後面的 `page.goto`，文件不會重新載入**：舊畫面的元素還在，`waitForSelector` 會先找到舊的。換頁一律走 `gotoView`（見「未解之事」第 1 筆）。
- **`getComputedStyle` 讀不到 `:visited` 的樣式**（瀏覽器的隱私保護）：已點過連結的顏色無法用程式量，只能禁止樣式表寫 `:visited` 規則。
- 其他已記在「踩過的坑」的平台行為（不重複）：Windows 上 subprocess 叫 `bash` 會找到 WSL bash；`pdftotext` 是 xpdf 4.00（沒有裁切參數）、`-table` 讀答案卷會整欄錯位；Write／Edit 工具會把 `\u00a0` 這類跳脫字寫成真的不可見字元；heredoc 裡的 `\n` 會被寫成真的換行；無頭瀏覽器的 `setOfflineMode` 管不到 Service Worker。

## 已知不一致與技術債

### 未解之事（沒有解決，只是暫時沒再發生）

1. **瀏覽器測試一次「1 項不符」，不知道是哪一項**（2026-10-08，加讀書模式時，`node scripts/test_browser.mjs` 本機模式）。
   - 經過：第一次跑回 `TEST-BROWSER FAILED：1 項不符`；我用 `sed` 只截了部分輸出，失敗的那一行不在截取範圍內。之後連跑 4 次都全綠，重現不出來。
   - 已知：不是「暫存目錄沒清掉」——那一項不計入不符項數（當時的總結行算的是 `fails`，暫存目錄另外判定）。所以是某一個 `check()` 失敗了。
   - **改善了什麼**：總結行現在直接列出不符項目的名稱（突變驗過）。這只解決「下次會知道是哪一項」。
   - **沒解決的**：那一次到底怎麼了。**連跑 4 次全綠不能證明沒問題，只證明它不是每次都發生**；間歇性的失敗最難查，也最可能在關鍵時刻出現。可能的方向（都未查證）：與其他專案同時跑 puppeteer 搶資源造成逾時、計時相關的檢查（模擬考倒數、撥時間驗尺的 600～603 秒範圍）、SW 安裝時機。
   - **新線索（2026-10-08，做外觀修正時）**：又出現一次間歇性紅，這次總結行有點名——「57 個細項逐一打開」，B.2 第 4 細項讀到了**上一個細項**的題目。原因查清楚了：測試用 `page.goto` 只改 `#` 後面時文件不會重新載入，App 的路由也不先清畫面，`waitForSelector('.study-q')` 會立刻找到上一頁還留著的元素。畫面要等 IndexedDB 讀完才換，窗口很窄，所以很少發生。**修法**：測試裡 44 處換頁全部改走 `gotoView`——先在 `#view` 放記號，換頁後等 `render()` 把它換掉才往下。**驗尺**：把畫面更新延後 300ms 撐大窗口，只用 `goto` 讀到上一頁 10／10 次，用 `gotoView` 0／10 次。（第一次試用 CPU 放慢 20 倍撐窗口，0／10 次，量不到——畫面是在等 IndexedDB，不吃主執行緒；驗尺沒證明抓得到之前不下結論。）
   - **這是不是第 1 筆那一次的原因：不知道。**那一次沒有點名，只能說「同一類競態可能造成那種結果」。所以這一筆維持「未解」，只把這個可能方向記下來。
   - **將來再出現「1 項不符」時，先把這一筆翻出來比對**：是哪一項、當時機器上還有什麼在跑、是不是計時相關的檢查。
